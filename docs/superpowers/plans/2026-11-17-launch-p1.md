# Launch P1: Reading and Polish Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** L. can finish and preview her drafts, and the public site (review page, home, cafes, about, stories) reads as one cohesive, accessible journal, ready for the impeccable launch gate.

**Architecture:**
- **Authoring follow-up first.** A full `ReviewEditForm` and an admin draft preview ship before any public polish.
- **One review renderer.** A pure view-model builder (`lib/review-view.ts`) turns cafe, visits, drinks and photos into a `ReviewPageView`. One server component (`ReviewArticle`) renders it. The public page and the admin preview differ only in input.
- **Fixtures for tests.** Visual and accessibility tests run against env-gated fixture routes (`/fixtures/...`), because the live database has no published reviews yet.
- **Named illustration slots.** A registry (`lib/illustrations.ts`) gives every illustration a slot name. Pages reference slots, never file paths, so the owner's picks swap in with one PR.
- **Parallel PRs.** Every PR owns a disjoint set of files (see the ownership map).

**Tech Stack:** Next.js 16 App Router (Server Components), React 19, TypeScript strict, Tailwind 4 with CSS tokens, Supabase (anon reads plus RLS, private photos with signed URLs), Vitest (added by P0 PR A), Playwright (smoke; this plan adds a 375px project and `@axe-core/playwright`).

**Spec:** `docs/superpowers/specs/2026-11-17-launch-design.md`. Read the whole spec, especially "Review page = layout A", "Visual system", "Illustrations" plus "Illustration direction (owner decision)", "Order of work" step 2, and "Launch gate". It builds on `docs/superpowers/plans/2026-11-17-launch-p0-authoring.md`.

## Global Constraints

- Hard rules from `AGENTS.md`:
  - Public reads use the anon client, and RLS is the guardrail.
  - Every Server Action calls `requireAuth()` before mutating.
  - Photos come from the private bucket through signed URLs (`lib/storage.ts`).
  - Nonce CSP (`proxy.ts`).
  - Commits use the noreply identity, never `--no-verify`.
  - CI must pass: typecheck, lint, build, unit tests, smoke tests.
- No database writes from any task here, and no new migrations. The schema is P0's 008 plus PR B's `009_listed_cafes_view.sql`. Public cafe reads (`getCafes`, `getCafeBySlug`, `getCafesForMap`) go through the `listed_cafes` view: published cafes with at least one published review. Keep it that way.
- No placeholder data or fake scores publicly. An unscored or empty thing renders nothing, never `0`, `3` or a gradient stand-in.
- Rating display:
  - Each drink and each visit is scored as a whole number 1–5.
  - The cafe score is the mean of published visits, rounded to 0.5 (`averageRating` in `lib/ratings.ts`).
  - Scores are shown as an IBM Plex Mono numeral in espresso, with a muted "/5". From two visits on: "4.5 · 2 visits".
  - No pink cups, hearts-as-rating, "yum!" or "meh".
  - The spec's "rating glyph is hand-coded SVG" becomes `RatingGlyph`: a small single-stroke espresso cup, decorative (`aria-hidden`), shown only beside the large header score. The numeral carries the meaning.
  - About explains the scale: "5 go out of your way, 4 we'd return, 3 fine, 2 skip, 1 no".
- Type roles:
  - Caveat (`font-heading`) for names and titles only.
  - Instrument Serif (`font-display`) for verdicts.
  - Mono for scores and metadata, 11px minimum (no `text-[10px]`).
- Contrast:
  - Terracotta `#C4735B` as text only at 24px and up, and only on cream. It is 3.35:1 on cream, but 2.97:1 on stone, which fails even the 3:1 large-text bar.
  - Buttons and small links use `terracotta-dark`, at least 4.5:1 on cream and stone.
  - Sage and pink are never text.
- Motion:
  - No entrance fades, staggers or `whileInView`. Content renders visible from the server.
  - Short hovers are fine.
  - Any remaining Framer Motion goes through `useMotionSafe()`.
- Layout:
  - One divider per page. No double frames (a bordered card around a rounded image).
- Illustrations:
  - Style B (owner decision, 2026-11-17): espresso ink `#2C2420`, clean fineliner, flat sparing accents in sage `#8BAA8F` and terracotta `#C4735B`.
  - The hero is a soft-edged ink-and-watercolour scene that blends into cream, with no frame.
  - All assets have transparent backgrounds.
- Public names are "Lea" and "Vids", from `profiles.display_name`. Repo docs use L./V.
- Public routes at launch: `/`, `/cafes`, `/cafes/[slug]`, `/about`, and `/stories` (linked in nav only once a story is published). `/map` keeps its route but gets no links.
- Coffee and matcha scope, with no coffee-only assumptions in names, routes or code.
- Small dev dependencies are allowed when named in the commit message. This plan adds one: `@axe-core/playwright`.

## Review Focus

1. **Date shift.** `date_visited = '2026-11-01'` renders "NOVEMBER 2026" in every timezone, never "OCTOBER 2026" (no `new Date('YYYY-MM-DD')` parsing). *Owner: Task E1 `formatMonthYear` tests.*
2. **A visit with photos but no cover chosen, or no photos at all.** The hero falls back to that visit's oldest photo, the same rule as P0's `pickCafeCover`, so the cafe card and the page hero agree. With no photos there's no hero: no gradient placeholder, no empty 3:2 box. *Owner: Task F1 `buildReviewPage` hero tests.*
3. **A photo that fails to sign** (CI's placeholder service key, an expired object). The query drops it. The page renders without that image, with no broken `<img>` and no empty strip. *Owner: Task F1 test `drops photos missing from input`, plus the Task G1 smoke run in CI (CI signs nothing).*
4. **Empty sections.** A visit with no drinks, no story or no tags omits that whole section, heading included. A legacy visit with `author_id = null` omits "BY …" and the byline. *Owner: Task F1 tests.*
5. **Story text as typed on a phone.** One Enter between paragraphs is the normal phone habit, so any run of newlines is a paragraph break. `\r\n`, trailing spaces and 3+ blank lines give the same paragraphs, with no empty `<p>`. Five or more paragraphs all render (the spec's 1–4 is guidance, not a cap). *Owner: Task E1 `toParagraphs` tests.*

- Rules for `buildReviewPage`. These algorithm choices are made here, not by the implementer:
  - **Visit order:** `date_visited` descending, then `created_at` descending.
  - **Lead visit:** `opts.leadVisitId`, if that visit is in the input; otherwise the first visit. No visits gives `null`.
  - **Earlier visits:** every other visit, in the same order.
  - **Score:** `value = averageRating(scores of all visits in input that are non-null)`, and `visits` counts the scored visits.
